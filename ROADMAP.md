# Roadmap

Status as of the 2026-10-21 review. Format: `- [ ] R<n> <title> — <what done means>`;

## Where the project stands

Updated 2026-10-22.

- Eight crates: `ppm` (CLI + package manager), `redirector` (injected Detours engine), `injection`
  (shared injection and the helper handshake), `test-probe` (live boundary probe), and the
  per-architecture build crates `engine-x86`, `engine-x64`, `probe-x86`, `probe-x64`. Five hooked
  isolation boundaries: registry CoW, process re-injection, credential vault, shell paths, process identity.
- Gates are green locally and in CI on x64 and ARM64: `cargo fmt --check`, `cargo clippy --workspace
  --all-targets -D warnings`, `cargo deny check`, and `cargo test --workspace` (176 tests, including
  the live e2e probes for x64, x86, a non-ASCII root, and refused unreachable children).
- Everything is on `main` on GitHub. A draft release v0.1.0 (x64 and ARM64 zips, each smoke-tested on
  its own architecture) awaits publishing; no tag exists yet.

## Side quests

- [x] S1 Badge monitor polls every 500 ms — `crates/redirector/src/shell/badge.rs` (`start_taskbar_monitor`) re-enumerates windows on a timer; a window event hook (create/show/hide) would end the polling. Seen while assessing R17 (ADR-008). Done 2026-10-22 (user chose event-driven): the monitor thread hooks `EVENT_OBJECT_SHOW` for its own process and puts a `WH_CALLWNDPROC` hook on each GUI thread that shows a window, which forwards `TaskbarButtonCreated`; no timer remains. Each process badges only its own windows, so the per-window `OpenProcess` scan is gone and windows of programs running outside virtualization are no longer badged. Verified live: a virtualized `charmap.exe` was badged on show and re-badged after a hide/show. Known gap documented in `watch_thread`: a reused GUI thread id is not re-hooked.
- [x] S2 Key creation reaches the host registry — after the e2e suites, the real `HKCU\Software\PPMTestProbe` holds 9 empty keys (`Tree\Child`, `Enumerated\Kept`, `DeleteKeyEx`, `AnsiEntryPoints\legacy_created`, ...) and no values: values are virtualized, but `RegCreateKeyEx*` creates the key on the host. Predates the ANSI work (the original suite's keys are there too). Seen 2026-10-21 reviewing `1264f02`. Fixed 2026-10-22: `create_key_virtually` creates in the overlay and only opens an existing host key (read access, caller's WOW64 view); the disposition comes from the overlay and the host. The fix exposed a store bug - re-creating a deleted key set the host masks on its live parent, hiding every host sibling - fixed in `materialize_chain` with a regression test. The e2e harness now seeds a real host tree per test (`tests/e2e_support/host_registry.rs`, root passed as `PPM_TEST_REGISTRY_ROOT`) and asserts it is exactly unchanged after the virtualized run; with the old create hook restored that assertion fails. The 9 old residue keys predate this and can be removed with `reg delete "HKCU\Software\PPMTestProbe" /f`.
- [x] S3 Cross-bitness injection trusts the helper's exit code — Detours' `DetourProcessViaHelperDllsW` treats `rundll32` exit 0 as success, but `rundll32` exits 0 even when it cannot load the DLL, so a helper that fails resumes the child with no engine. Seen on the first ARM64 CI run (39708194996): the ARM64 build used the native `system32\rundll32.exe`, and x86 children ran uninjected. That cause is fixed (DETOURS_OPTION_BITS for ARM64); verifying the child actually received the engine before resuming it would close the class. Fixed 2026-10-22 for every injector that can read its child: `inject_suspended` requires Detours' restore payload in the suspended child (`DetourFindRemotePayload`) and refuses the spawn without it. Regression `test_e2e_a_child_the_engine_cannot_reach_is_refused_rather_than_run_unvirtualized` swaps in an x86 engine the helper cannot load: before the fix the x86 child ran unvirtualized ("FOLDERID_Profile was not redirected"), now its spawn fails. The x86-injector-to-64-bit-child route is left as S5.
- [x] S4 Metadata responses skip the HTTP status check — the four strategies in `package/version.rs` parse the body of any response, so a 404 or 500 from a release endpoint surfaces as a JSON/YAML parse or missing-key error instead of the status. The downloader checks it. Seen 2026-10-22 while threading `HttpClients` through for R30. Fixed 2026-10-22: one `fetch_metadata` helper rejects non-success statuses for all four strategies. The regression test serves a 503 whose body is a valid release document; before the fix the check returned it as release 9.9.9, now it fails naming the 503.
- [x] S5 A 32-bit injector cannot verify a 64-bit child's injection — `DetourFindRemotePayload` from an x86 process cannot see a 64-bit child's memory above 4 GiB (the x86 probe's x64 peer failed the S3 check though it was injected), so `can_inspect` skips the check on that route and it still trusts the helper's exit code. Closing it needs a check the 32-bit side can make, e.g. a handshake from the engine before the child's entry point runs. Seen 2026-10-22 while fixing S3. Fixed 2026-10-22: the engine's ordinal-1 export (`ppm_finish_helper`) does the helper's work, verifies the restore payload from the child's bitness, and sets a per-child named event the injector created; the injector refuses the spawn unless it is set. Regression `test_e2e_a_native_child_of_an_x86_application_is_refused_when_its_engine_cannot_load`: before the fix the native child of the x86 probe ran unvirtualized ("FOLDERID_Profile was not redirected"), now its spawn is refused.
- [~] S6 Released binaries reported a stale version — the release workflow computed the tag from conventional commits and never read Cargo.toml, so v0.1.1's `ppm.exe --version` printed 0.1.0 (also the HTTP User-Agent). Fix: the tag is derived from Cargo.toml's version, the workflow refuses a pushed tag that disagrees or a version already released, and the smoke test requires `ppm --version` to match the tag (proven locally: it rejects the v0.1.1 zip). Done once v0.1.2 is released and reports 0.1.2.
